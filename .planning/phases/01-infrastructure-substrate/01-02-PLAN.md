    2. Sleep 2s to allow WAL flush.
    3. Query via SQL: `curl -X POST "$IOX_URL/api/v3/query_sql" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"db": "demo-org.metrics", "q": "SELECT * FROM cpu WHERE host = '"'"'smoke-test'"'"' ORDER BY time DESC LIMIT 1", "format": "json"}'`.     4. Repeat the same write+read cycle against `demo-org.logs` and `demo-org.traces` (use measurement names `app_log` and `span` with minimal fields). Assert each returns the written row.
    5. Print `OK: IOx 3-signal roundtrip verified` on success.

    **Status:** Accepted — 2026-11-12

    **Context:**
    - STORE-01 requires 3-day hot tier (satisfied by IOx 3 Core OSS ≤72h).
    - STORE-02 requires 30-day warm tier.
    - STATE.md flags the 72h boundary as HIGH-severity blocker with three candidate resolutions: (a) InfluxDB 3 Enterprise license, (b) separate IOx instance with extended config, (c) custom compactor derived from open-source IOx code.
    - Local retention-boundary probe results from `/tmp/iox-retention-probe.json` are quoted inline.

    **Decision:**
    Adopt **option (c) hybrid**: IOx 3 Core OSS as the authoritative hot tier (≤72h), and the 30-day warm tier implemented as a distinct storage lane — specifically, a Parquet-on-MinIO/S3 tier managed by a dedicated warm-tier compaction service deferred to Phase 2 (built by the Metrics/Logs ETL Workers that flush from IOx to object store). No InfluxDB Enterprise license dependency in v1. Warm-tier queries are served by the Query Orchestrator (Phase 4) via DataFusion `ListingTable` against the same cold-tier partition scheme (`tenant_id/signal_type/dt=YYYY-MM-DD/`) — warm and cold differ by SSD vs. remote object store caching, not by partition layout. This avoids the one-way-door risk of a layout change between warm and cold.

    **Rationale:**
    - Option (a) violates PROJECT.md "Apache 2.0 — no GPL/LGPL dependencies in core" (Enterprise is not Apache 2.0 — adopting it breaks the OSS positioning).
    - Option (b) doubles operational complexity of IOx without extending what OSS Core can do.
    - Option (c) reuses the cold-tier infrastructure we must build anyway (STORE-03 is in-scope for this phase, Plan 3) and keeps the OSS-only promise. The only additional engineering is a periodic flush job, which Phase 2's ETL Workers already need for cardinality enforcement.

    **Consequences:**
    - IOx databases in all phases are created with `retention_period_hours: 72` (or less), never higher. The bootstrap script enforces this by reading `namespaces.json` which pins all retentions to 72.
    - "Warm tier" and "cold tier" share the same S3 partition scheme and differ only by SSD cache residency. Phase 2 must build the flush path before Phase 4 Query Orchestrator can query across tiers.
    - If OSS Core later adds configurable retention beyond 72h, revisit this ADR; do not silently increase retention in `namespaces.json`.

    **Open issues:** None that block Phase 1. Flush-service design is Phase 2 scope.

    Also add a `## Alternatives Considered` section citing options (a) and (b) with the rejection reasons above, and a `## Links` section pointing to STATE.md, PROJECT.md constraints, and ROADMAP.md Phase 1 success criterion #3.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IOx HTTP API :8181 | Receives line-protocol writes and SQL queries; token-authenticated |
| IOx → MinIO (S3) | IOx flushes Parquet files to object store; credentials passed via env |
| IOx database namespace | Logical tenant boundary within a single IOx cluster (no per-namespace CPU/IO quotas per ARCHITECTURE.md — noted as future HIPAA tiering concern) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Spoofing | IOx auth token in env var | accept | Local-dev scope; token `local-dev-token` is documented as non-production. Production deployment (Phase 7) sources token from Vault via ESO (STACK.md Layer 8). |
| T-01-07 | Tampering | IOx namespace retention bypass | mitigate | `namespaces.json` pins retention ≤72h; `bootstrap.sh` reads only this file; ADR 0001 forbids ad-hoc `retention_period_hours > 72`. Code review enforces. |
| T-01-08 | Information Disclosure | Cross-namespace query leakage | mitigate | Every query includes an explicit `db=<name>` parameter; IOx enforces namespace isolation at the API layer. Noted for Phase 2: ingest service must set `db` from authenticated tenant context, never from client input. |
| T-01-09 | Denial of Service | Unbounded IOx WAL growth (cardinality) | mitigate | Deferred to Phase 2 (STORE-04 series cap at ingest gate). Phase 1 ADR notes that uncapped writes will trigger WAL cascade (PITFALLS.md Pitfall 3) — enforced before any external data flows. |
| T-01-10 | Elevation of Privilege | IOx admin token reuse across orgs | accept | Single admin token for local dev is acceptable. Production will use per-service scoped tokens (Phase 2 ingest, Phase 4 query orchestrator each get their own). |
| T-01-SC | Tampering | npm/pip/cargo installs | mitigate | No package-manager installs in this plan. Container image `influxdb:3-core` is pinned to the `3-core` tag; replace with pinned digest before production (Phase 7). |
</threat_model>
